# 故事结构质量治理说明

## 目标

本 Skill 的故事结构维护采用“过程数据库 + 最终交付文件”双层设计：

- `故事结构_增量.json`：过程数据库，服务于逐章上下文、断点续跑、信息积累。
- `故事结构.json`：最终交付文件，服务于高质量结构化分析、后续创作、改编和检索。

逐章阶段不追求每一轮 `故事结构_增量.json` 文学整理质量完美，但必须保证它结构合法、引用自洽、来源可追踪、错误可回滚。

## 为什么不采用每章全量重写

每章让模型读取上一版完整JSON并返回新版完整JSON，会带来以下风险：

1. JSON越到后面越大，输入和输出都膨胀。
2. 模型可能遗漏旧角色、旧事件、旧伏笔。
3. 模型可能静默改写前面已经确定的信息。
4. 某一章输出质量差，会污染整个全局结构。
5. 断点恢复时很难判断是哪一章改坏的。

因此，本 Skill 只允许模型在逐章阶段输出 `Delta/Patch`，不允许每章输出完整新故事结构。

## 四层治理

### 第一层：章节分析与Delta提取分离

章节分析器只输出 MD：

```text
当前章节原文 -> 第N章_章节分析.md
```

Delta提取器再读取：

```text
当前故事结构_增量.json + 当前章节原文 + 第N章_章节分析.md
```

只输出：

```text
第N章_delta.json
```

这样可以让文学理解和严格结构化分开，提高JSON稳定性。

### 第二层：Delta入库前校验

合并前必须运行：

```bash
python validate_delta.py <故事结构_增量.json> <第N章_delta.json>
```

检查：

1. JSON格式是否合法。
2. 顶层字段是否符合规范。
3. 新增元素是否有完整标准字段。
4. 修改元素是否只包含合法增量字段。
5. 字段类型和值域是否正确。
6. 是否存在未知字段。
7. 是否存在空名称。
8. Delta内部是否存在重复名称。
9. 是否引用不存在的人物、地点、阵营、事件、线索、物品。
10. 新增元素是否其实已存在于当前结构。
11. 每个新增/修改元素是否在 `详情` 中提供非空 `提取理由`；它必须留在章节分析、Delta、治理补丁和变更日志，而不是最终元素 JSON。
12. 角色生日是否为合法 ISO 时间；事件时间是否等于最小涉及章节对应的章节时间。
13. 事件涉及章节是否为固定宽度、升序、去重字符串，事件数组是否按最小涉及章节非递减，分组段号是否按连续剧情段顺序递增，是否存在非连续复用同一剧情段名称；事件分组是否尽量采用 `段号-剧情段名+剧情线主题+叙事功能+爽点情绪点+冲突悬念类型`。

不通过则不得合并，只重跑Delta提取器。

### 第三层：合并后全量过程库校验

合并后必须运行：

```bash
python validate_structure.py --chapter-check <故事结构_增量.json> <第N章_delta.json>
```

该模式保留 `--chapter-check` 名称用于兼容既有命令，但实际语义是：对合并后的整个 `故事结构_增量.json` 执行 `process` 级全量检查，并在报告中附带本章 Delta 触碰元素数量。它不是最终强校验，也不是只检查本章触碰元素的局部校验。

三档检查分工：

```text
每章提交后：全量 process 检查
  保证过程库整体可读、字段/类型/骨架合法，可继续下一切片。

周期/按需治理后：全量 governance 检查
  引用错误升级为 error，用于发现治理补丁、合并、重命名、降级带来的全局问题。

最终交付前：全量 final/strict 检查
  强 Schema、引用、最低数量、介绍完整性等核心质量项必须全部通过。
```

检查重点：

- 本章事件的参与成员是否存在。
- 本章事件的发生地点是否存在。
- 本章线索涉及事件是否存在。
- 本章角色所属阵营和关系引用是否存在。
- 本章阵营父级和座落地点是否存在。
- 本章地点父级是否存在。
- 本章详情字段中的 `类型:名称` 引用是否存在。

失败时回滚到合并前快照，只重跑Delta提取器。

### 第四层：周期审计与最终整理

每5-10章触发一次结构审计，审计器读取：

```text
当前故事结构_增量.json
最近5-10章章节分析MD
最近5-10章Delta JSON
最近一次快照
```

审计目标：

1. 合并重复角色/地点/阵营/物品。
2. 识别别名被当成新元素的问题。
3. 降级临时路人和无持续价值元素。
4. 调整事件粒度。
5. 整理伏笔和线索。
6. 补充缺失关系。
7. 标记需要进一步复核的冲突，并将其作为下一次自动修复的输入。
8. 对治理新增的历史聚合事件按最小涉及章节插入；对既有事件只允许重分类，不允许改变时间、涉及章节或数组位置。
9. 治理后按事件数组顺序全量重排剧情段号，并把非连续重复的剧情段拆为独立段名；分组名优先保留/补足 `剧情段名+剧情线主题+叙事功能+爽点情绪点+冲突悬念类型` 的页面摘要；跨段主题、线索关联和视觉信息仍以标签和详情为准，不用于决定连续剧情段。
10. 标签治理只保留支持跨元素检索、筛选、聚合或导航的标签。每项 `治理操作.治理标签` 必须给出保留标签、降级标签和理由，二者完整覆盖原标签集；降级标签以可逆 JSON 字符串数组写入 `详情.补充标签`，不允许静默丢弃。

审计器输出 `correction_delta.json`，不得直接覆盖完整JSON。

自动运行时，周期审计不构成人工暂停点。`run_pipeline.py run` 在每个周期点执行：

```text
生成/更新 audit_001-005.md
↓
调用配置的自动审计器生成 correction_001-005.json
↓
validate_delta --mode governance → merge_delta → apply_governance_ops → validate_structure --mode governance
↓
失败则把审计器输出和校验反馈写入 audit_001-005.feedback.md，再自动重试
↓
通过后才进入下一章
```

自动审计器通过 `--audit-command` 或 `NOVEL_AUDIT_COMMAND` 配置。命令模板可使用 `{project_dir}`、`{audit_pack}`、`{correction_path}`、`{feedback_path}`、`{chapter_start}`、`{chapter_end}`、`{attempt}`。`--governance-retries` 表示首次失败后的最大重试次数，默认 `3`（最多共尝试4次），`0` 表示不重试；单次审计器默认900秒超时，可通过 `--audit-timeout-seconds` 在600-1800秒间调整。审计器没有配置、超时或重试耗尽时，主控会失败关闭，不会把未治理的结构带入下一章。

周期补丁可以用顶层 `章节范围` 表示审计范围；该字段只在 `validate_delta.py --mode governance` 中有效。逐章 Delta 仍必须使用单章 `章节` 字段。

最终阶段允许模型生成完整 `故事结构_草稿.json`，但必须经过：

```bash
python validate_structure.py --strict <故事结构_草稿.json>
```

通过后才能写入 `故事结构.json`。

## 回滚策略

每章合并前保存：

```text
故事结构版本/story_before_chNNN.json
```

每章合并通过后保存：

```text
故事结构版本/story_after_chNNN.json
```

若某章校验失败：

1. 用 `story_before_chNNN.json` 覆盖 `故事结构_增量.json`。
2. 保留失败的Delta和校验报告。
3. 重跑Delta提取器。
4. 再执行入库前校验、合并、章节级校验。

若后面才发现某章污染结构：

1. 找到最近可信快照。
2. 从该快照后一章开始重放Delta。
3. 对可疑章节强制重跑Delta提取器。

## 过程JSON与最终JSON的边界

`故事结构_增量.json` 允许：

- 某些角色简介还不够精炼。
- 某些事件粒度需要最终统一。
- 某些伏笔需要后续判断是否有效。
- 某些人物关系处于待确认状态。

但不允许：

- JSON格式错误。
- schema不合法。
- 关键字段缺失。
- 本章新增/修改元素交叉引用错误。
- 无依据覆盖旧事实。
- 无法追踪来源章节。

`故事结构.json` 必须：

- 去重完成。
- 引用自洽。
- 分组统一。
- 事件顺序合理。
- 伏笔/线索质量高。
- 人物关系清晰。
- 符合 `story_structure_spec.md`。
