# Delta 提取与合并规则

Delta提取器负责读取：当前故事结构(或摘要) + 章节原文 + 章节分析MD，并输出纯 JSON（本章增量）。

## 提取规则

1. **只输出本章Delta，不输出完整故事结构JSON**。
2. 新元素放入 `新增元素`，必须提供完整标准字段。
3. 已存在元素放入 `修改元素`，只填本章新增/变化字段，不要重写旧元素。
4. 通过名称和别名判断是否已有元素，别名不要当成新人物。
5. 每个 `新增元素` 和 `修改元素` 都必须在 `详情` 中提供非空 `提取理由`。它保留在章节分析、Delta、治理补丁和变更日志中，不合并进最终元素 JSON。角色、地点、线索、阵营、物品必须在 `详情` 中提供 `首次章节`、`最近章节`；事件必须在 `详情` 中提供 `涉及章节`；`其他事项集`只要求公共字段，不伪造章节追溯字段。
6. 角色必须有 ISO `生日`，未知固定为 `0001-01-01T00:00:00`。事件必须有章节时间 `时间` 和位于详情中的固定宽度、升序、去重的 `涉及章节`，例如 `0043，0044，0045`。
7. 事件数组按最小涉及章节排序；治理新增历史聚合事件时按该位置插入，修改既有事件不得移动位置。事件分组推荐使用复合格式 `段号-剧情段名+剧情线主题+叙事功能+爽点情绪点+冲突悬念类型`，例如 `0010-退婚事件+情感尊严线+冲突爆发+羞辱反击+身份与尊严`；同一完整分组只能覆盖一个连续事件区间，治理后按事件数组顺序重排全部段号。
8. 跨剧情段主题写入 `标签集`，丰富语义写入 `详情.剧情段`，正式线索关联写入 `详情.关联线索`（例如 `线索:退婚约定`）。视觉资产入口写入 `标签集`，具体画面生产资料写入 `详情.视觉等级`、`详情.画面类型`、`详情.核心画面`、`详情.镜头建议`、`详情.氛围`、`详情.视觉理由`、`详情.视觉用途`。
9. 不确定信息不得写成确定事实，应放入 `详情` 中的“疑似信息/待确认信息”一类字段，或写入 `冲突声明`。
10. 临时路人、一次性地点、无持续价值物品不要轻易进入主要元素集；必要时写入事件详情。
11. 事件粒度要统一：事件应代表有叙事功能的剧情推进，不要把每句动作拆成事件。
12. 伏笔/线索必须有后续价值或明显悬念，不要把普通描述泛化成线索。
13. 所有交叉引用必须指向当前结构已有元素或本Delta新增元素。
14. 每个事件介绍必须描述参与成员在事件中做了什么。
15. 受控标签必须与 `references/narrative_taxonomy.json` 完全一致；角色只使用 `人物类型:*`；事件可使用剧情母题、叙事功能、冲突对象/议题、悬念问题/风险/机制、剧情线主题、爽点情绪点、冲突悬念类型、画面类型、视觉用途；其他事项只使用 `自由主题:*`。不带这些受控前缀的普通标签保持自由。
16. `叙事功能:*` 是普洛普 31 项的可选分析参照：不要求任何作品或章节覆盖 31 项，不要求按普洛普顺序出现，也不参与事件排序、最低数量或质量门槛。只在原文确有对应时标注。通俗的“开篇铺垫/冲突升级/转折/高潮”等功能可以写在复合分组第3段或普通标签中。
17. `剧情线主题:*`、`爽点情绪点:*`、`冲突悬念类型:*` 用于事件横向筛选；`画面类型:*`、`视觉用途:*` 用于筛出视觉资产候选。具体视觉描述不要塞进标签，写入详情或全书分析/视觉资产。
18. `自由主题:*` 收纳有价值的周边信息，包括但不限于世界规则、设定体系、叙事机制、主题母题、零散灵感、还没归类的设定、备用支线、彩蛋、创作备注等。不得把已经属于角色/事件/地点/线索/阵营/物品的事实放入其中。此标签不强制限制内容。
19. **标签自动压缩**：每章 Delta 生成后、合并到过程库后，`run_pipeline.py` 会自动调用 `scripts/compress_tags.py`，把所有带受控前缀（`剧情母题:`、`叙事功能:`、`人物类型:`、`画面类型:` 等出现在 `narrative_taxonomy.json` 顶层键中的前缀）的标签从 `标签集` 机械下层到 `详情.补充标签`，并按 `references/tag_limits.json`（事件 12、其余 8）对剩余自由标签 FIFO 截断、超额部分一并下层。这是确定性脚本步骤，不依赖 LLM。LLM 仍按本文档前述规则尽可能产出有语义的受控标签，只是最终落盘前会重新分配标签到 `标签集` 和 `详情.补充标签` 两个槽位。所以 LLM 遇到「未知受控标签」校验错误时，不要在 repair 中删除整批前缀；写出来即可，由脚本统一下层。

## 合并语义

`merge_delta.py` 对 `新增元素` 和 `修改元素` 采用字段级深度合并，**只增不删**：

| 字段类型 | 合并方式 |
|:---|:---|
| 元素匹配 | 按 `名称` -> `别名` 顺序查找；别名命中时合并到主元素 |
| `介绍` | 追加去重，不覆盖已有介绍 |
| 列表字段 | 去重合并，保持原顺序在前 |
| `详情` | 键级递归合并；累计来源、提取理由和旧版首次/最近章节不进入最终元素，完整追溯仅保留在过程产物 |
| 标量字段 | Delta非空覆盖，空值/缺省跳过 |
| 顶层 `介绍` | 标题非空覆盖，描述追加去重 |

## 入库前校验

每章 Delta 生成后，必须先运行：

```bash
python scripts/validate_delta.py <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

如果返回非0：
- 不允许 merge。
- 不重跑章节分析器。
- 只重跑 Delta提取器。
- 将校验报告保存到 `质量治理/delta校验/第{seq:03d}章_{title}.json`。

严格模式可用于质量优先场景：

```bash
python scripts/validate_delta.py --strict <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

## 合并后全量过程库校验

合并前先备份：

```bash
cp <项目目录>/故事结构_增量.json <项目目录>/故事结构版本/story_before_ch{seq:03d}.json
```

合并：

```bash
python scripts/merge_delta.py <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

合并后立即检查整个过程库：

```bash
python scripts/validate_structure.py --chapter-check <项目目录>/故事结构_增量.json <项目目录>/章节处理/第{seq:03d}章_{title}.json
```

`--chapter-check` 的名字保留兼容旧命令，但实际语义是：每个切片合并后，对合并后的 `故事结构_增量.json` 执行全量 `process` 检查，并在报告开头列出本切片 Delta 触碰元素数量。它不是“只检查本章触碰元素”的局部校验。

如果失败：
```bash
cp <项目目录>/故事结构版本/story_before_ch{seq:03d}.json <项目目录>/故事结构_增量.json
```
然后只重跑 Delta提取器。

如果通过：
```bash
cp <项目目录>/故事结构_增量.json <项目目录>/故事结构版本/story_after_ch{seq:03d}.json
python scripts/progress_manager.py update <项目目录> 2 '{"已完成章节": [...], "总章节数": N}'
```

## 增量JSON膨胀应对

| JSON大小 | 输入策略 |
|:---|:---|
| < 80KB | 完整传给 Delta提取器 |
| 80-200KB | 传元素名称摘要 + 最近10章Delta，必要时按需读取完整JSON |
| > 200KB | 传主角/主要阵营/最近10章摘要，按需读取局部详情 |

即使只传摘要，Delta提取器也必须遵守：**修改元素只输出本章新揭示的信息，不凭摘要重写旧定义**。
